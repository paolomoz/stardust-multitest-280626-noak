# STARDUST plugin findings — sony run (2026-06-28)

Log of things that generalize to the stardust PLUGIN itself (bugs, friction, improvement ideas).

Format: [phase/skill] observation → suggested fix.

## Phase 1 — Extract
- [extract/crawl.mjs] BUG (high impact): bot-management fallback only triggers when `probe.goto` THROWS (H2/QUIC/connection-reset). Akamai (and similar enterprise WAFs) return a clean **HTTP 403** to headless chromium — Playwright's `goto` does NOT throw on 4xx — so the headed-Chrome fallback never fires and the entire crawl fails with `HTTPError: HTTP 403` on every page. sony.com reproduces this 100%. → After the probe `goto`, also check `response.status()` for 403/429/503 and trigger the headed `channel:'chrome'` fallback. (Patched locally in my copy; one-line fix in crawl.mjs main().)
- [extract/crawl.mjs] The bundled crawler `import { chromium } from 'playwright'` resolves node_modules relative to the SCRIPT's directory (skill source tree), which has no node_modules, so running it in place fails ERR_MODULE_NOT_FOUND even after `npm i -D playwright` in the project. Had to copy crawl.mjs into the project tree to run it. → Either resolve playwright via the project root explicitly, or document copying it into the target.

## Phase 2-3 — Direct / Prototype
- [extract→prototype] The bundled crawl.mjs captures a LIGHTER schema than the full extract recipe: no per-section computed-style summary, no palette/type aggregation, no logo locator chain, no screenshots, no _brand-extraction.json, and no PRODUCT/DESIGN authoring. Yet the extract SKILL.md presents crawl.mjs as "a runnable reference implementation of this whole sub-command." In practice the agent must hand-run Phases 3-6 (brand surface, current-state docs, brand-review.html) separately. → Either expand crawl.mjs to emit the brand-surface + per-section styles, or relabel it as "Phase 2 capture only" in the skill so the agent budgets for the rest.
- [extract/crawl.mjs] crawl.mjs does not record the provenance fields the SKILL's own contract requires (`waitMs`, `waitMode`, `httpStatus`) — it writes `renderedBy`/`fetchedAt` only. `validateProvenance()` in downstream phases would fail on these records. → align crawl.mjs output with the live-render-evidence contract (add waitMs/waitMode/httpStatus).
- [extract image-fidelity] For bot-managed origins (Akamai), captured image URLs 403 to curl/hotlink even though they render in-browser. The deploy image-fidelity gate ("curl must 200 or omit") would wrongly drop every real image. The robust path is to download captured media THROUGH the browser context and host locally. → extract should optionally persist captured media binaries locally (the schema mentions assets/media/ but crawl.mjs doesn't populate it), and the deploy gate should treat "renders in headless browser" as the fidelity check for bot-managed origins, not curl.
- [prototype/impeccable] The impeccable design hook re-reports earlier findings by their ORIGINAL line numbers after an edit shifts lines (reported "layout-transition:76" as still present when 76 now contained the fixed code). Mildly confusing in an autonomous loop. → re-scan and remap line numbers, or mark stale findings resolved.
- [prototype/impeccable brand.md] Inter is on impeccable's reflex-reject font list, but Mode A identity-preservation (SST→Inter substitute) is the correct call. brand.md does carve this out ("identity-preservation wins") — worth surfacing this carve-out more prominently to avoid the hook/critique flagging a pinned substitute.

## Phase 5-9 — Deploy / Rollout / Verify
- [deploy] Path-safety bites at PREVIEW, not just delivery: a DA path with an underscore (`/sony/.../purpose_and_values`) PUT 201 fine but `POST /preview/` returned 404 persistently; normalizing `_`→`-` fixed it immediately. The deploy skill's path-safety guidance frames `_`→`-` as a delivery concern; it should call out that the admin PREVIEW step itself 404s on underscore segments. deploy-batch.mjs reports it only as a generic "preview-fail preview 404" — a path-safety hint there would save a debugging round-trip.
- [deploy] Folder-index trailing-slash asymmetry: a nested home at DA `/sony/index` is served ONLY at `/sony/` (trailing), while `/sony` (no trailing) AND `/sony/index` both 404. This is the inverse of the skill's blanket "EDS docs have no trailing slash — strip it" rule. The rule is right for leaf docs but wrong for a folder index (logo/home links must KEEP the trailing slash). The link-audit guidance should special-case the folder-index home path, or the authoring generator will emit a 404-ing bare `/sony` logo link (it did; caught only by GETting links against the live tree).
- [deploy/rollout] query-index did NOT materialize on the feature branch: `helix-query.yaml` committed+pushed, source pages published to live, both `/sony/news-index.json` and the default `/query-index.json` 404 on .aem.page AND .aem.live after re-publish + polling. Indexing appears unreliable/absent on a non-main feature branch. The rollout/deploy guidance ("query-index builds against the LIVE tree — publish in the loop") omits that branch previews may never build an index at all. → Either document that dynamic indexes require main (or an explicit index-trigger admin call), or have rollout surface "index not built" as an explicit post-deploy check rather than assuming publish ⇒ index. (Mitigated here by the news block's authored fallback, which the skill recommends — that saved delivery.)
- [deploy] deploy-batch.mjs is excellent (idempotent ledger, delivered .plain.html check before flip, concurrency). One gap: when a page is renamed/relinked, stale ledger entries must be hand-pruned to force a re-drive; a `--force <path>` or content-hash check would avoid editing the ledger JSON by hand.
- [deploy media] content `<img>` must be DA-hosted (content.da.live), so 23 captured images had to be uploaded to DA media via a hand-written PUT loop. The deploy skill describes the upload contract but ships no media-upload helper alongside deploy-batch.mjs — a `upload-media.mjs` companion (read referenced imgs, PUT to /media, rewrite srcs) would close the loop the skill already documents.

## Phase 0 — Setup
- [extract/setup] Master SKILL.md (stardust setup step 2) references the impeccable context loader as `scripts/load-context.mjs`, but the actual file is `scripts/context.mjs`. Running the documented path fails with MODULE_NOT_FOUND. → Fix the path in stardust/SKILL.md to `context.mjs` (or rename the script).
- [extract/setup] On a vanilla aem-boilerplate target, `npm i -D playwright` fails with ERESOLVE (boilerplate pins eslint@8 while @babel/eslint-parser@8 peer-wants eslint@^9). Skill says "run npm i -D playwright" but doesn't mention the boilerplate peer-dep conflict; needs `--legacy-peer-deps`. → extract setup should note the boilerplate eslint peer conflict and recommend `--legacy-peer-deps` (or use the global/MCP Playwright).
- [extract/setup] Impeccable is installed under a versioned path `cache/impeccable/impeccable/<version>/skills/impeccable/`. Stardust setup says look in standard harness dirs (`.claude/skills/` etc.) but the plugin-cache layout has an extra `<version>` segment and a doubled `impeccable/impeccable`. Loader discovery had to be done by `find`. → document the plugin-cache path shape or have a resolver helper.
