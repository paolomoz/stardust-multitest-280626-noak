## Phase 0 — Setup
- (2026-06-28) Repo arrived as vanilla `aem-boilerplate` (head.html loads `aem.js`/`scripts.js`, no `ak.js`/`postlcp.js`/`lazy.js`). The prompt anticipates this and routes to the `stardust:deploy` Runtime bootstrap, but the *extract/direct/prototype* skills run fine before that — bootstrap is only needed at deploy. Noting the ordering held up.
- (2026-06-28) `.gitignore` in the boilerplate did NOT exclude `.env*`, `qa/`, or `samples/` (only `.hlx`, `coverage`, `logs`, `node_modules`). Phase 0 requires these excluded. Suggest the deploy bootstrap (or a scaffold step) enforce these `.gitignore` entries automatically.
- (2026-06-28) DA token smoke-test: `GET /source/{org}/{repo}/` and `/source/{org}/{repo}` both return 404 on an empty repo folder, which is ambiguous vs auth failure. `GET /list/{org}/{repo}` returns 200 and is the reliable auth smoke-test. Suggest skills document `/list/` as the canonical token smoke-test endpoint.

## Phase 1 — Extract
- (2026-06-28) The bundled crawler `skills/extract/scripts/crawl.mjs` does `import { chromium } from 'playwright'`, but it lives in the skill directory. When playwright is installed in the TARGET project's `node_modules` (per the skill's own setup guidance), ESM module resolution walks up from the *script's* location (the skill dir), NOT the project, so the crawler throws `ERR_MODULE_NOT_FOUND` even though playwright is correctly installed in the project. Had to copy `crawl.mjs` into the project (`qa/crawl.mjs`) and run it there. Suggest: skill should instruct copying the crawler into the project root before running, or resolve playwright via an absolute path / the project's node_modules explicitly.
- (2026-06-28) `npm i -D playwright` fails with ERESOLVE on the stock aem-boilerplate `package.json` (peer-dep conflict among the boilerplate's lint/test devDeps). Needed `--legacy-peer-deps`. Suggest the extract setup note mention `--legacy-peer-deps` for aem-boilerplate targets.

## Phase 2-3 — Direct / Prototype
- (2026-06-28) The bundled `crawl.mjs` (extract engine) produces ONLY `pages/*.json` + `_crawl-log.json`. It does NOT emit `_brand-extraction.json`, current-state `PRODUCT.md`/`DESIGN.md`/`DESIGN.json`, or `brand-review.html` (extract skill Phases 3-5). Those are left to the agent, but the skill text reads as if the crawler does them. Either the crawler should emit a starter brand-surface, or the skill should state explicitly "Phases 3-5 are agent authoring on top of crawl.mjs output."
- (2026-06-28) Splash/redirect entry pages: the site root `/` was a 4s `<video>` + `setTimeout(window.location='/home')` splash. The crawler captured the splash (0 links/headings) and stopped — BFS found nothing because the real site is at `/home`. extract's discovery should detect a meta/JS refresh or near-empty body with a single redirect and follow it (or surface "entry is a redirect → real content at X"). I had to notice the 99KB mainTextLen-vs-0-links mismatch manually and re-crawl from /home.
- (2026-06-28) impeccable design hook is quite aggressive on prototype files (flagged alpha-gradient video scrims as `design-system-color`, the metric-match fallback `Arial`/`Times New Roman` @font-face as `overused-font`). These are exactly the brand-faithful inversions the deploy/direct skills bless. The hook has no awareness of the stardust Mode-A brand-faithful inversions list, so every faithful render trips it. Suggest the hook read `DESIGN.json#extensions.divergence.brand_faithful_inversions[]` and auto-dismiss matching findings (the prototype SKILL already specs this auto-dismiss for critique/audit, but the live PostToolUse hook doesn't do it).

## Phase 4-9 — Migrate / Deploy / Rollout
- (2026-06-28) `deploy-batch.mjs` is excellent (resumable ledger, delivered `.plain.html` verify-before-flip, bounded concurrency). The one gap: it verifies on `aem.live` by default tld, which worked, but a `verify-fail about:error` (the nav fragment's root-relative `/icons/` logo) is reported as a generic FAIL without hinting that a repo-relative `<img>` in authored content is the classic cause (#9). A targeted message ("about:error often = repo-relative /img in content; move fixed chrome assets into block code") would speed diagnosis.
- (2026-06-28) Chrome logo placement: authoring the brand logo as an `<img src="/icons/...">` inside the DA nav FRAGMENT delivers `about:error` (ingester can't fetch the repo-relative path as content media). Correct pattern (per deploy anti-pattern 9b) is to inject the fixed logo from the header BLOCK JS root-relative. Worth calling out explicitly in the deploy Step 6 header recipe as the default for the logo specifically (the skill says it for CSS backgrounds but the logo-in-fragment trap is easy to hit).
- (2026-06-28) Query-index (`helix-query.yaml`) did NOT auto-materialize after first publish — `/<idx>.json` 404s even though config was pushed before the publish wave. The index appears to need pages re-published AFTER Code Sync has the config live (a race), or an explicit re-index. The rollout/deploy skills say "index builds against the LIVE tree" but don't give the concrete trigger (re-publish after config sync, or POST admin /index). A documented "force-reindex" step would help. Mitigated here by authoring static fallback content in the listing blocks so pages are never empty.
- (2026-06-28) Gzipped code assets: verifying a deployed block's JS with `curl | grep` silently fails because aem.page serves `content-encoding: gzip`; must use `curl --compressed`. An until-loop polling for a deployed code change can hang forever on the compressed bytes. Minor, but a verify-helper in the skills should use `--compressed`.
